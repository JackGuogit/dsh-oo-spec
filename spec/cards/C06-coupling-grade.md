## 判定

### 八级耦合（从优到劣）

| 级 | 名称 | 识别特征 | 处置 |
|---|---|---|---|
| 1 | 无耦合 | 什么都不依赖 | **不一定好**：每个轮子自己造 |
| 2 | 消息耦合 | 只传消息/事件，不传数据 | 最优目标态 |
| 3 | 数据耦合 | 通过参数传**基本数据** | 可接受 |
| 4 | 数据结构耦合 | 通过参数传**数据结构/对象** | 关注：传了整个对象但只用两个字段 → 收窄参数 |
| 5 | 控制耦合 | 传入**控制参数**改变对方行为 | 高发区：`if (type == 1)` → 用多态替换 |
| 6 | 外部耦合 | 共用外部格式/协议/设备接口 | 不可避免，收敛到适配层 |
| 7 | 全局耦合 | 共享全局数据/单例 | 优先消除 |
| 8 | 内容耦合 | 直接读写对方内部成员 | **病态**，必须改 |

### 三条反直觉判断

1. **无耦合不是最优。** 完全自给自足 = 放弃复用，效率极低。合理的依赖是分工。
2. **低内聚和高耦合本质是同一件事：不稳定。** 判据不是"依赖数量"，而是"改一个地方会波及多少"。
3. **耦合不是越低越好。** 把耦合降到 0 通常意味着把逻辑复制到每个调用方。

### 处置流程

```
1. 列出依赖，逐条定级（用上表）
2. 定级 ≥5 的：找变化点，用 C07/C08 处理（控制参数→多态；全局数据→注入；内容耦合→封装）
3. 定级 ≤4 的：只在"改动波及面"变大时才动
4. 循环依赖：一律处理，不允许留在交付物里
```

## 何时不适用

- 与第三方 SDK/协议对接：外部耦合不可避免，只要求收敛在适配层，不要求消除
- 性能敏感的底层模块：可能刻意选择更紧的耦合换取性能，需在交付物里写明理由

## 反例

| 错法 | 症状 |
|---|---|
| 追求零依赖 | 每个类自己连数据库、自己写日志文件 |
| 只看依赖数量 | 10 个依赖全是消息耦合被判为"耦合过高" |
| 用继承复用 | 父类改一个字段，20 个子类编译失败（内容耦合的变体） |
| 控制参数滥用 | `service.handle(type)` 里 15 个 if 分支 |

## 依据

- 八级耦合依次恶化，内容耦合又称"病态耦合"（8.2.2）
- 完全无耦合的模块"每个轮子都要自己发明，效率非常低下"（8.2.2.1）
- 低内聚、高耦合的本质都是"不稳定"；真正好的设计是在高内聚和低耦合间平衡（8.5 小结）
