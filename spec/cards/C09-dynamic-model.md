## 判定

### 四种动态模型，按问题选一种

| 模型 | 回答什么问题 | 什么时候用 |
|---|---|---|
| **状态模型** | 一个对象在生命周期里有哪些状态、怎么迁移 | 有明确状态机（订单、支付、工单）；有"非法操作"要拒绝 |
| **活动模型** | 一个流程的步骤与分支、并发 | 跨多个对象的业务流程；有审批/分支/并行 |
| **序列模型** | 一次交互中对象之间的消息时序 | 要说明"谁先调谁"；接口协作复杂；排错 |
| **协作模型** | 对象之间的结构关系与职责分配 | 要说明"谁负责什么"而非时序 |

### 选型规则

```
有状态且状态影响可用操作 → 状态模型（优先）
跨对象的多步流程 + 分支 → 活动模型
单次交互的时序争议 → 序列模型
职责分配争议 → 协作模型
```

一个功能通常**一张就够**，复杂时最多两张（状态 + 序列）。

### 三条建模技巧（硬约束）

1. **不要面面俱到**：只画有争议、有分支、有并发、有状态约束的部分。正常流一句话能说清就不画。
2. **模型 ≠ 代码**：模型是给人看的意图表达，不追求能生成代码；不要为了"图能对得上代码"而画满。
3. 画完问一句：这张图解决的是哪个具体争议？答不出来就删。

## 何时不适用

- 单对象、单方法、无状态：不需要动态模型
- 已有可运行的实现且无争议：图是负债不是资产

## 反例

| 错法 | 症状 |
|---|---|
| 四张图全画 | 交付物 40 页图，没人看，代码与图不一致 |
| 用序列图代替状态机 | 状态迁移散落在 6 个方法里，非法操作拦不住 |
| 把模型当代码 | 图上标了 `private`、`List<Order>`、方法签名 |
| 画了正常流没画异常流 | 与 C02 的失败模式同源 |

- 建模技巧：不要面面俱到；模型 != 代码（6.3.3）
