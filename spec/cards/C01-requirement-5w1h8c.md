## 判定

### 第 0 步：先做价值测试（不要先画功能）

对客户说的每一句，问：**这件事对客户有价值吗？**

- 有价值 → 是**需求**
- 是系统为了实现价值而提供的能力 → 是**功能**

```
客户说"我要个 POS 机"
  ├─ 需求层：买单（顾客付钱拿走商品）  ← 有价值
  └─ 功能层：商品扫描、金额汇总、收银、打印小票  ← 是实现手段
```

判错方向的代价：按功能建模 → 领域模型里出现一堆技术过程实体，业务一变全崩。

### 第 1 步：填 5W1H（功能属性）

按 When → Where → Who → What → Why → How 顺序填。每槽必须落到具体值，不许写"一般情况"。

- `Who` 找**参与者**，不找人：系统、设备、外部服务都算参与者
- `When` 要问作息：凌晨 2–4 点做的数据倒换工具，和一键式工具是两个设计
- `Where` 要问国别与室内外：影响合规、设备形态、网络假设

### 第 2 步：填 8C（质量属性）

性能、成本、时间、可靠性、安全性、合规性、技术性、兼容性。

**功能属性 + 质量属性缺一不可**：功能全对但一次操作 10 分钟，等于没做对。

### 第 3 步：出缺口清单

14 槽里凡不能给 `KNOWN` 的，进入 `10-flow-gates.md` 的分诊流程。

## 何时不适用

- 纯技术重构、无业务方 → 不需要 5W，但仍要 8C（性能/兼容性决定重构边界）
- 已有完整 PRD 且 14 槽齐备 → 只做校验，不重填

## 反例

| 错法 | 症状 |
|---|---|
| 把功能当需求 | 需求列表 = 界面控件清单 |
| 8C 只填性能 | 上线被合规卡住 / 集成阶段爆炸 |
| Who 只写"用户" | 权限模型做不出来，后期补鉴权 |
| 照着客户给的方案做 | 客户说 POS 机就做 POS 机外观和收银台，没问"买单" |

## 依据

- 需求 = 对客户有价值的事情；功能 = 系统为实现客户价值而提供的能力（4.1）
- 5W 是需求的上下文，"环境影响需求"；同样一个垃圾桶，贫民窟与帝国大厦要求完全不同（4.3.2.1）
- 5W1H 是功能属性，8C 是质量属性，两者缺一不可（4.3.2.3）
