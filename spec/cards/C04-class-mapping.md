## 判定

三步，顺序不可换。跳步是设计失控的主要原因。

### 第一步 照猫画虎：领域类 → 软件类

按四小步走，每步只做一件事：

```
1. 筛选     哪些领域类要进软件系统？（给出理由）
2. 名称映射 留下的领域类 → 同名软件类（先一对一，不做优化）
3. 属性映射 领域属性直接搬过来（先不做分组与派生）
4. 关系映射 领域关系 → 引用/集合/关联
```

判据：
- 每个软件类必须能指向某个领域类，或标为"辅助类"（辅助类第三步才允许出现）
- 筛选必须写理由，不能整批搬过来，也不能整批丢掉
- 这一步**不许**出现接口、抽象类、设计模式

### 第二步 精雕细琢：套原则与模式

只处理**第一步之后看出来的变化点**。

```
对每个候选抽象位置：
  1. 说出变化点（什么会变、怎么变）
  2. 给出时间窗（半年/1年/2年/3年，见 L0 #8）
  3. 若时间窗内变化概率低 → 不做抽象，记账即可
  4. 若要做 → 套 C07 定原则，C08 选模式
```

判据：没有"变化点 + 时间窗"的抽象一律回退。

### 第三步 照本宣科：拆辅助类

工具类、工厂、DAO/Repository、DTO、转换器。这类类**没有业务语义**，在领域模型里本来没有对应物。

判据：辅助类的用途能一句话说清，且不承载业务规则（承载了就应该回到第二步当领域类处理）。

## 何时不适用

- 一次性脚本/原型：可只做第一步，但要在交付物里写明"未做精雕细琢"
- 既有系统内加功能：只对新增/变更的类跑三步，不动存量类

## 反例

| 错法 | 症状 |
|---|---|
| 第一步就上模式 | 还没看清变化点，先抽出 `AbstractOrderFactory` |
| 跳过筛选 | 领域模型 20 个类全部进软件，代码里 8 个没人用 |
| 辅助类抢跑 | 设计一开始就有 `OrderHelper`、`CommonUtil`，业务规则散落其中 |
| 精雕细琢变成重构狂欢 | 一遍设计改了 30 个类，没有一个变化点有依据 |

## 依据

- 类从哪里来：不是想象力、不是参考其他系统、不是拍脑袋，而是领域模型（6.2.1）
- 领域类→软件类"基本上就是一个照猫画虎的过程"，但要先做类筛选（6.2.1）
- 第二步：应用设计原则和设计模式；第三步：拆分辅助类（6.2.2 / 6.2.3）
