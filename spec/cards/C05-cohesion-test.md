## 判定

### 核心判据（唯一充要条件）

> **模块内的元素是否都专注于模块的职责？**

不是"元素之间是否互相调用"。这条判据直接推翻了最常见的直觉。

### 三步测试

```
1. 写出这个模块的职责，一句话
2. 逐元素问：它是否只为这个职责服务？
     是 → 保留（哪怕元素之间毫无调用关系，如 CRUD）
     否 → 记录，进入 3
3. 不属于该职责的元素，是否构成另一组内聚的职责？
     是 → 拆（按新的职责边界拆，不是按方法数拆）
     否 → 移到它该去的地方，或删
```

### 功能内聚的判定技巧（最容易被滥用的一级）

"单一任务"很模糊，用 **all contribute to** 卡：所有元素都是为了同一个任务，**缺一不可**。

反测：如果某个元素还能服务于别的任务，那就不是功能内聚。

```
readFile() 里的 checkFileExist / checkFilePrivilege / openFile / read
→ 这些方法同样能服务 writeFile、deleteFile
→ 不是 all contribute to → 是过程内聚，不是功能内聚
→ 但它们确实都为了"读文件"这个任务而按序执行 → 保留，不拆
```

### 内聚不是越高越好

- 盲目追求功能内聚 → 类被切碎，调用链变长，改动要跨 5 个文件
- CRUD 类：方法互不调用，但内聚很高 → **不许拆**
- 真正的目标是在高内聚与低耦合之间**平衡**，不是单边最大化

## 何时不适用

- 纯数据传输对象（DTO/Entity 直通）：结构由外部契约决定，不做内聚判定
- 框架强制的类（Controller/Filter）：职责由框架定义

## 反例

| 错法 | 症状 | 正确做法 |
|---|---|---|
| 按方法数拆 | "超过 10 个方法就拆" | 按职责边界拆 |
| 把"互不调用"当低内聚 | 拆了 CRUD 类 | 保留，看职责 |
| 为 SRP 把 8 行函数拆成 3 个类 | 类多于概念 | 保留，用注释表达意图 |
| 用工具的直觉判内聚 | `utils` 包被判为"最差内聚"就删掉 | 偶然内聚确实最差，但 Utils 包的存在有其合理性，评估使用成本后再决定 |

## 依据

- 内聚 = 凝聚力；"是否专注模块的职责，才是内聚性的充要条件"（8.1.1）
- 功能内聚的判据是 "all contribute to"，所有元素缺一不可（8.1.2.7）
- CRUD 类方法互不依赖但内聚很高（8.1.1 反例）
- 内聚性不是越高越好；好的设计是在高内聚和低耦合间平衡（8.3 / 8.5 小结）
- 职责是站在他人的角度定义的，不是自己定义的（8.5 小结）
