## 判定

三字经，顺序固定：**找名词 → 加属性 → 连关系**。

### 第一步 找名词

1. 打开用例文档，把**所有名词**挑出来（含用例描述、异常分支、约束）
2. 只从用例里找。不从表结构、不从旧代码、不从"业务上应该有"
3. 同一概念的不同说法合并（"顾客/买家/用户"→ 若是同一角色则合一）

判据：**每个领域类都能指到用例原文的某一句**。指不到 → 删掉或回 G1 补需求。

### 第二步 加属性

- 属性 = 描述该名词状态的数据（`商品: 条形码、名称、价格`）
- 属性不是类。`价格` 不该单独成类，除非它自己有生命周期和行为
- 属性来源：用例里提到的 + 约束里隐含的

### 第三步 连关系

- 每条关系必须有：方向、重数（`1..n` / `0..1` / `1..1`）、语义名
- 关系类型是领域语义（持有、属于、参与），不是数据库外键

### 关键判断：参与者 vs 实体

| 情况 | 处置 |
|---|---|
| 业务参与者，但系统内不需要实现（`顾客` 之于 POS 软件） | **不转软件类** |
| 设备，且无界面相关需求（`屏幕/键盘/扫描仪`） | 不转软件类 |
| 设备，且有"同时支持图形界面与字符界面"这类需求 | 转软件类 |

## 何时不适用

- 纯算法/中间件系统：领域概念少，可从既有架构文档取词（但需注明来源）
- 已有领域模型，只做增量需求：只对新增用例跑三字经，并检查与既有模型的一致性

## 反例

| 错法 | 症状 | 后果 |
|---|---|---|
| 从数据库表反推 | 类名 `t_order`、`order_item` | 模型被 schema 绑死 |
| 属性立类 | `金额`、`数量` 各成类 | 类爆炸，关系混乱 |
| 关系只连线 | 没有重数 | 一对多写成一对一，代码里补集合 |
| 把顾客建模成实体 | 领域模型出现 `Customer` 但不承担任何系统职责 | 后续为了"用上它"硬造功能 |

## 依据

- 领域建模的方法就是"找名词"，从需求模型（具体是从用例）中找（5.1–5.2）
- 找到名词后"加属性、连关系"（5.1）
- POS 机实例：经筛选后保留 `收银员、商品、交易、小票、支付、信用卡、会员卡、现金、购物卡` 转为软件类；`顾客` 与输入输出设备不转（6.2.1）
