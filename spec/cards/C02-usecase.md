## 判定

### 用例必须四段齐全

```markdown
【用例名称】<动宾，如"买单"、"踩">

【场景】
Who:
Where:
When:

【用例描述】
1. ...
   1.1 <异常分支：条件 + 系统反应 + 谁做什么>
2. ...

【用例价值】
<一句话：用户通过这个用例能得到什么>

【约束和限制】
<业务规则、额度、频次、权限边界>
```

### 强制要求

1. **异常流 ≥ 2 条**，写在主流程对应步骤下（编号 2.1 / 2.2 / 2.3）
2. 每条异常必须给**处置**，不能只写"失败"
3. 用例只描述**用户与系统的交互**，不描述内部实现
4. 一条用例 = 一个用户可感知的价值，不是一串技术步骤

### 自检问句

- 把每条描述读一遍，问：这一句是用户能感知的吗？不是 → 删或降为实现细节
- 每条异常问：谁发现了这个异常？系统怎么反应？用户看到什么？
- 用例价值写不出来 → 这个用例不该存在（回到 C01 做价值测试）

## 何时不适用

- 纯批处理/定时任务：没有交互 → 用活动图或状态机替代（见 C09）
- 已有用例但只是补异常流 → 只跑"异常流 ≥2"这一条

## 反例

```
【用例描述】
1. 用户点击踩
2. 系统写入数据库
3. 返回成功

（错在：没有异常流；"写入数据库"是用户不可感知的实现细节；
  缺"约束和限制"，导致恶意刷踩无上限）
```

书中的正例在同一用例里给了异常分支，并明确写了约束"单用户每天踩的次数不超过 100 次"（11.1.2）。

## 依据

- 用例描述的是 5W1H 中的 How（4.4）
- 用例写作分两步：第一步正常处理，第二步异常处理（11.1.2）
- 场景段固定 Who / Where / When；用例必带"用例价值"与"约束和限制"（11.1.2）
