## 判定

### 唯一入口：先找变化，再谈模式

```
1. 找到变化：什么会变？怎么变？多快变？
2. 定时间窗：互联网≈半年 / 电信≈1年 / 金融≈2年 / 政府≈3年
3. 时间窗内不会变 → 不引入模式，直接写（记账即可）
4. 会变 → 封装变化：把变化点隔离到一个可替换结构里
5. 需要现成结构 → 查 tables/variation-to-pattern.md 选型
```

**"找到变化"回答 Where，"封装变化"回答 Why。** 23 个模式只回答 How。

### 找不到变化时的兜底与终止条件

若对领域不熟、不知道什么会变：

- 兜底：假设一切都会变（"唯一不变的是变化本身"）
- **必须设终止条件**：只封装「有限时间内可能发生的变化」
- 否则会陷入变化递归：A 变成 B，B 又变，无穷无尽，系统做不出来

### 原则 vs 模式（别混用）

| | 指导什么 | 形式 |
|---|---|---|
| 设计**原则** | 指导"如何定义"（类、接口、依赖的方向） | 判定条件（见 C07） |
| 设计**模式** | 指导"如何组织结构" | 可复用的类结构 |

顺序：先用原则定形状，再用模式套结构。反过来会出现"为了塞进模式而扭曲职责"。

### 模式只是锤子

- 模式解决的是"结构"问题，不解决"职责划分"问题。职责错了，套什么模式都错。
- 一个系统里到处是模式，通常是变化点没识别对。

## 何时不适用

- 只有一个实现、且时间窗内不会增加 → 不引入（NOP）
- 变化点在数据而非行为（字段增减）→ 用配置/表结构，不用模式
- 团队/代码库已有既定惯例 → 跟随惯例，优先一致性

## 反例

| 错法 | 症状 |
|---|---|
| 为模式而模式 | 只有一个 `WechatNotifier`，先抽 `NotifierFactory` + 接口 |
| 变化点说不清 | "以后可能要支持多种支付"（无时间窗、无具体形态） |
| 用模式替代职责划分 | 上帝类套上 Facade，还是上帝类 |
| 一次上三个模式 | 装饰器 + 工厂 + 策略包一个 50 行的功能 |

## 依据

- 设计模式之道 = "对变化的概念进行封装" / "找到变化，封装变化"（9.3.2）
- "找到变化"解决 where，"封装变化"解决 why（9.3.3）
- 终止条件 = 有限时间内可能发生的变化；时间窗参考值随行业不同（9.3.3）
- 设计模式只是一把锤子（9.2）；原则与模式是互补的（9.4）
