# 内聚七级判定表（L3）

用法：`cards/C05` 的判定步骤第 2 步之后查本表，确认"当前形态"属于哪一级，再决定处置。

| 级 | 内聚类型 | 划分依据（元素为何被放在一起） | 典型形态 | 处置 |
|---|---|---|---|---|
| 1 | 偶然内聚 | 纯属巧合 | `utils` / `misc` 包，各类职责互不相关 | 最差；按实际用途拆开，或明确标注为"工具箱"并限制其增长 |
| 2 | 逻辑内聚 | 逻辑上属于同一宽泛类别，但职责不同 | `input` 包含 Mouse、Keyboard；`output` 包含 Printer、Display | 弱；按具体职责拆，或保留为类型分组（分类而不承载行为） |
| 3 | 时间内聚 | 在时间上相近发生 | 异常处理函数里"释放资源 + 记日志 + 通知用户" | 常见于函数级；可接受，但一旦各自需要复用就拆 |
| 4 | 过程内聚 | 必须按固定顺序执行 | `readFile`：判断存在 → 判断权限 → 打开 → 读 | 常见于函数级；**不因"方法互不调用"而拆** |
| 5 | 信息内聚 | 共同操作同一份数据（又称通信内聚/联系内聚） | 一组方法都读写同一个订单对象 | 较好；关注是否有人只用到其中一部分数据 |
| 6 | 顺序内聚 | 前一个元素的输出是后一个的输入（流水线） | 解析器输出执行计划 → 执行器消费执行计划（规则引擎） | 好；注意上下游是否会被独立替换 |
| 7 | 功能内聚 | 所有元素都为同一个单一任务，**all contribute to（缺一不可）** | HTTP 协议解析、XML 解析、个税计算 | 最好；但"单一任务"含义模糊，必须用 all contribute to 验 |

## 功能内聚的反向测试（必做）

逐元素问：**这个元素还能服务于别的任务吗？**

- 能 → 不是 all contribute to → 不是功能内聚（通常是过程/顺序内聚）→ 但这**不等于要拆**
- 不能，缺它就完不成这个任务 → 功能内聚

例：`readFile` 的 `checkFileExist / checkFilePrivilege / openFile` 同样能服务 `writeFile`、`deleteFile` → 过程内聚。但它们为"读文件"这一任务按序服务，保留。

## 三条总则

1. **判定依据是"是否专注模块职责"，不是元素之间的调用关系。**
2. **CRUD 类：方法互不依赖，但内聚很高 → 不拆。**
3. **内聚不是越高越好**；目标是高内聚与低耦合之间的平衡。
