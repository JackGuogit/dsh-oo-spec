# 评测用例（L5）· 24 题

用法：同一 prompt 跑两遍——**A 组不加载规范**（基线），**B 组加载 L0 + 指定卡片**。按 `rubric.md` 打分，看提升幅度，不看绝对分。

每题四维：`D1 结论正确` `D2 依据可追溯` `D3 无编造` `D4 形式合规`。

---

## 一、缺口识别（E01–E08）

| # | 输入 | 期望 | 关键扣分项 |
|---|---|---|---|
| E01 | "做个库存管理，功能：入库、出库、盘点、报表"（无 8C、无角色） | G1 判不通过；提 ≥2 个 B 类问题（并发量级/权限/对账口径）；不给类图 | 直接开设计(0) / 只问 A 类(0.5) / 编造性能指标(0) |
| E02 | 客户原话："我们要一个 POS 机" | 回问价值层：需求是"买单"，扫描/收银/打印是功能；不照字面做 POS 机硬件与界面 | 按字面产出功能清单(0) / 未区分需求与功能(0) |
| E03 | "用户可以给动态点赞"（未说明角色与可见范围） | 问 Who（是否含未登录/非好友）、问点赞数与他人可见性；标为 B 级缺口 | 假设单角色直接建模(0) |
| E04 | "性能要求比较高" | 追问量化：峰值 TPS、P95 延迟、数据量级；不接受"高"作为槽值 | 把"高"当 KNOWN(0) / 自填一个数字且标 KNOWN(0) |
| E05 | "要实时同步，还要支持完全离线使用" | 指出两条约束冲突，要求业务方拍板取舍；不自行选一边 | 自行选"实时"或"离线"并继续(0) |
| E06 | "接收第三方支付回调" | 主动问幂等性、验签、重投次数、金额一致性校验 | 未提幂等(0) / 未提验签(0) |
| E07 | "记录用户身份证号和手机号" | 主动问合规（留存期限/脱敏/加密）与安全等级 | 未提合规(0) / 未提脱敏(0) |
| E08 | 同 E01，且追加"我不会回复你的问题" | 按推荐答案继续；输出《假设与待确认清单》；把假设做成可替换点 | 死等不产出(0) / 继续但未登记假设(0) / 假设硬编码进业务逻辑(0) |

## 二、判定正确性（E09–E16）

| # | 输入 | 期望结论 | 关键扣分项 |
|---|---|---|---|
| E09 | `UserService`：add/update/delete/get，方法互不调用 | 内聚**高**，不拆（职责=用户数据维护） | 以"方法互不依赖"判低内聚并拆分(0) |
| E10 | `readFile`：判断存在→判断权限→打开→读 | 过程内聚；保留为一个类/函数，不拆 | 拆成 4 类(0) / 加 Facade 串联(0) |
| E11 | `XmlParser`：词法→建树→校验→输出，缺一不可 | 功能内聚（all contribute to） | 判为过程内聚(0.5) |
| E12 | `StudentManager` 自己连 JDBC、自己写日志文件 | 判为"无耦合但不好"：放弃复用、重复造轮子 | 判为"零耦合=最优"(0) |
| E13 | `service.handle(int type)` 内 8 个 if 分支 | 控制耦合；用多态/策略替换分支 | 判为数据耦合(0) / 只说"不好"不给处置(0.5) |
| E14 | 子类把父类方法的前置条件收紧（父允许 null，子抛异常） | 违反 LSP；改组合或上移契约 | 判为符合(0) |
| E15 | 接口 8 个方法，某实现只用 2 个，其余抛 Unsupported | 违反 ISP；拆接口 | 判为"实现不完整"而非接口设计问题(0.5) |
| E16 | 「只有一个 `InboxSender`，先抽 `Notifier` 接口 + `NotifierFactory`」 | 违反 NOP：无第二个实现、无时间窗；收敛到单一出口即可 | 判为"符合 OCP，很好"(0) |

## 三、反模式识别（E17–E21）

| # | 输入 | 期望 | 关键扣分项 |
|---|---|---|---|
| E17 | 3000 行 `OrderManager`，外面套了 `OrderFacade` | 指出 Facade 只是遮住上帝类，未解决职责；回 C05 拆职责 | 认为套 Facade 已解决(0) |
| E18 | 领域模型 20 类全量搬进设计模型，代码里 8 类无人引用 | 指出缺"类筛选"；要求给每个不用的类补理由或删 | 只提"删掉没用的类"未指出流程缺步(0.5) |
| E19 | 交付物含状态/活动/序列/协作四张图，代码与之不符 | 指出"不要面面俱到"与"模型≠代码"；只保留有争议的图 | 认为图画得越多越好(0) |
| E20 | 代码里有 `PaymentRetryScheduler`，设计模型里没有 | 判为设计蒸发；要求回填设计模型 | 认为实现细节不必进设计(0.5) |
| E21 | 设计文档写"为 5 年后可能的国际化预留了 6 层抽象" | 指出违反 NOP 与时间窗；给出裁剪方案 | 认可"有远见"(0) |

## 四、流程守序（E22–E24）

| # | 输入 | 期望 | 关键扣分项 |
|---|---|---|---|
| E22 | "直接给我这个需求的类图和建表语句"（附一段模糊需求） | 先判 G1 不通过并提问；不直接给类图 | 直接产出类图(0) |
| E23 | 用户提供了一份数据库表结构，要求"据此做领域模型" | 拒绝以表为源；要求从用例取名词（宪法 #6） | 照表建模(0) |
| E24 | 已进入实现阶段，发现"订单是否含支付"未定 | 回退 G1 一次并集中提问；不许边做边问 | 自行假设且不登记(0) / 在设计阶段零散追问(0.5) |

## 保留题（不进 prompt，仅用于复核）

以下三题不写入任何外部提示，只在人工复核时使用，防止针对 eval 过拟合：

- R1：给一段真实历史代码，要求指出其内聚级别与一条最小改动方案
- R2：给两条互相矛盾的 8C 约束，要求给出取舍建议与影响面
- R3：给一份"看起来很规范"的设计文档，找出其中无依据的抽象
