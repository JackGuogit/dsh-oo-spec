# 00 · 宪法（L0，12 条）

生效范围：所有设计、编码、评审、需求分析任务。冲突时本文件优先于卡片的建议。

---

## 1. 先定输入，再产出

任何设计或代码产出前，必须能指出它对应哪条用例编号。指不出来 → 停下提问，不许先写。

- 判定：交付物首行有 `依据: UC-xx`。无 → 违反。
- 出处：第 3 章（技术流程：需求模型→领域模型→设计模型→实现模型）

## 2. 不编造业务规则

缺口处写 `TODO(BLOCKING:"<要问什么>")` 或标 `ASSUMED`。行业惯例、"通常做法"不得当作客户需求写入。

- 判定：交付物出现无来源的业务数字/状态/规则 → 违反。
- 例外：技术性选择（命名、日志、内部数据结构）可直接决定，并登记到假设清单。

## 3. 需求 ≠ 功能

客户给的是解决方案时，回问价值层。判定问句：**这件事对客户有价值吗？** 无价值的是功能，有价值的是需求。

- 反例：客户说"我要个 POS 机" → 需求是"买单"，"商品扫描/金额汇总/收银"是功能。
- 出处：4.1（ATM / POS 机 / 汽车 / 打印机 四例）

## 4. 缺口三态制

5W1H8C 共 14 槽（见 `10-flow-gates.md`），每槽必须落为 `KNOWN` / `ASSUMED` / `UNKNOWN` 之一。

- `UNKNOWN` 且 B 级 → 闸门不通过，禁止进入下一阶段。
- 判定：14 槽有空槽 → 违反；`UNKNOWN` 未标级别 → 违反。
- 出处：4.3.2（5W1H8C）+ 本包新增的三态约束

## 5. 顺序不可跳

需求模型 → 领域模型 → 设计模型 → 实现模型。跳步必须在交付物里写明「跳了什么、为什么、怎么补偿」。

- 判定：产出类图但无用例来源 → 违反；写代码但类图上没有 → 违反（除非已回填）。
- 出处：第 3 章

## 6. 领域模型只从用例取名词

不从数据库表、不从别人的代码、不从"我觉得应该有的实体"取。每个领域类必须能指到用例原文中的名词。

- 判定：存在无法指向用例的领域类 → 违反。
- 出处：5.1–5.2（"从用例中找名词"）

## 7. 以"变化"为唯一驱动

引入抽象、接口、模式前，必须先说出**具体的变化点**。说不出 → 不引入。

- 判定：新增抽象无对应变化点说明 → 违反。
- 出处：9.3.2（"找到变化，封装变化"）

## 8. 抽象必须有变化时间窗

"未来可能变"不算理由。必须给时间窗：互联网 ≈ 半年 / 电信 ≈ 1 年 / 金融 ≈ 2 年 / 政府 ≈ 3 年。

- 判定：变化点说明里没有时间窗 → 违反。
- 出处：9.3.3（有限时间内可能发生的变化；时间窗为书中参考值）

## 9. 内聚看职责，不看调用关系

方法之间互不调用不构成拆分理由（CRUD 类内聚很高）。判定问句：**这些元素是否都只为这个模块的职责服务？**

- 出处：8.1.1（内聚的充要条件是"是否专注模块职责"）

## 10. 不确定性封装成可替换点

假设、外部依赖、可能变的部分，做成接口/配置/策略类，不散落在业务代码里。

- 判定：同一处不确定性在 ≥2 个业务方法里以硬编码出现 → 违反。
- 出处：9.3.3（封装变化 = 把影响范围缩到最小）

## 11. 交付物必须自证

每个设计决定附一行依据（用例号 / 约束 / 变化点）。无依据的决定标记为「待确认」。

- 判定：设计文档中无依据的决定 → 计入待确认，不得计入已完成。

## 12. 提问有规格

一次 ≤5 题，按阻塞度降序；每题给「推荐答案 + 一行理由 + 选错的后果」；禁止开放式提问；声明不回复则按推荐继续。

- 判定：单轮 >5 题 → 违反；出现"你想怎么做？"→ 违反；未声明默认动作 → 违反。

## 冲突优先级

```
#2 不编造  >  #5 顺序  >  #7 变化驱动  >  #9 职责判定  >  其余条文  >  卡片建议
```

- 质量约束（8C 中的安全性、合规性、兼容性）压过一切设计偏好，包括"高内聚低耦合"。
- 当两条建议冲突且本表无法裁决 → 按宪法 #12 提问，不要自选。
