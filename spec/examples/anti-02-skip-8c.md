# 反例 02：8C 全空，直接开设计

## 错误产出

```text
需求："做一个支付回调接收服务，把第三方支付结果同步到我们系统"

AI 产出：
  1. CallbackController
  2. PaymentCallbackService
  3. PaymentRecord 表设计
  4. 重试机制：失败重试 3 次
  ...  直接给出类图和建表语句
```

没有做 G1，14 槽里至少 6 槽是空的。

## 缺了什么，后果是什么

| 缺的槽 | 真实后果 |
|---|---|
| 性能（回调并发量级） | 按低频设计，大促时回调积压，订单状态停更 |
| 可靠性（能不能丢、能不能重复） | 没做幂等 → 同一笔回调处理两次 → 重复发货 |
| 安全性（签名校验、来源 IP） | 任何人都能伪造回调把订单改成已支付 |
| 兼容性（第三方字段会不会变、要不要支持多渠道） | 上线两周接第二家支付，全部重写 |
| 合规性（支付数据留存要求） | 日志里打了完整卡号，审计不通过 |
| Who（谁是参与者：第三方、我方、财务、客服） | 对账与人工补单需求缺失，运营要手工核 |

**其中"幂等"和"签名校验"是重构级代价**：已经是上线后才发现，要改数据、退款、补单。

## 正确做法

G1 不通过就不许进 G2。此时应输出：

```markdown
【G1 需求闸门 · 5 项阻塞缺口】（≤5 题，按阻塞度降序）

Q1 同一笔支付结果可能回调几次？我方要求"最多处理一次"还是"可重复"？
   推荐：可能重复，必须幂等（以第三方交易号 + 状态机做幂等键）
   理由：第三方回调普遍至少一次投递，网络重试无法避免
   选错的后果：重复发货/重复记账，需人工冲正

Q2 回调并发量级是多少？（峰值 TPS、单日总量）
   推荐：按峰值 200 TPS 设计，异步落库 + 快速 ACK
   理由：你没给数字，先按中小型电商估
   选错的后果：同步处理导致超时，第三方判定失败并重投，雪崩

Q3 是否只接一家支付渠道？未来 12 个月是否要接第二家？
   推荐：抽象出渠道适配层（1 个接口 + 1 个实现）
   理由：支付渠道变更在零售业属高概率事件，时间窗 2 年
   选错的后果：接第二家时改调用方

Q4 安全要求：是否强制验签 + 来源 IP 白名单 + 金额一致性校验？
   推荐：三项全做
   理由：无验签等于开放写接口

Q5 支付相关数据的留存与脱敏要求？（能否记录完整卡号/手机号）
   推荐：全量脱敏，仅留后四位

未回复的按推荐继续，并输出《假设与待确认清单》。
```

## 触发这条反例的信号

- 交付物第一页是类图或建表语句，找不到 14 槽表
- 8C 只填了"性能：高"
- 出现"通常做法是……"作为业务规则依据
- 需求里出现金额、状态、外部回调，却没有幂等/验签/对账设计
