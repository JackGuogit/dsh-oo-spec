# 黄金链路：合格的产出长什么样

分三段。**A / B 是书中实证**（可直接对照原文，锚点见 `rag/anchors.md`），**C 是按流程推导的示例**（书中未给出完整代码，此处只演示该写什么、写到什么程度）。

---

## A · G1 需求模型：朋友圈「踩」

### 5W（书中原文口径）

| 槽 | 值 |
|---|---|
| When | 用户浏览朋友圈动态的时候 |
| Where | 虚拟空间是"朋友圈"，物理空间不限（家里、公交、地铁、咖啡馆均可） |
| Who | 开通了朋友圈的用户 |
| What | 用户对某条动态进行"踩"，发动态的用户能看到"踩"的信息 |
| Why | 有人转发虚假信息、无用鸡汤文、诱导广告，其他用户通过"踩"表达态度和情感 |

**5W 分析后必须做的一步：找隐含风险。** 本例的结论是——朋友圈是亲密关系圈，"踩"可能影响关系，这一点必须在需求与功能设计时考虑（书中原话）。这一步不能省，它是 5W 的唯一产出物。

### 1H（用例）

两个核心用例：`踩`、`取消踩`。用例四段齐全：

```markdown
【用例名称】踩
【场景】Who: 微信用户 / Where: 朋友圈 / When: 浏览朋友圈时
【用例描述】
1. A 进入朋友圈，看到 B 发的自己不喜欢的动态
2. A 点击互动弹出框，出现 踩 / 赞 / 评论 三个选项
3. A 点击"踩"
4. 被踩动态下方显示：踩的数量、踩的用户名称列表
5. C 浏览该动态时，若与 A 是好友关系，则能看到这条踩的信息
【用例价值】用户可以通过"踩"表达对某条动态的态度和情感
【约束和限制】为防止恶意"踩"，单用户每天踩的次数不超过 100 次
```

异常处理（书中要求"第二步：异常处理"，此处按该要求补齐三条示例）：

```markdown
2.1 用户未开通朋友圈 → 提示开通，不展示互动入口
3.1 该用户已踩过这条动态 → 按钮置灰，不允许重复计数
3.2 当日踩的次数已达上限 → 提示"今日次数已用完"，不写入
5.1 浏览者与 A 非好友 → 只显示数量，不显示用户名称列表
```

### 8C（本例必须给的项）

| C | 值 | 为什么必须给 |
|---|---|---|
| 性能 | 点击"踩"后 ≤200ms 反馈 | 社交互动，慢即放弃 |
| 安全性 | 需登录态；防刷（与每日 100 次上限配套） | 恶意刷踩 |
| 兼容性 | 与既有"赞/评论"共用互动弹出框与计数展示 | 书中的 5W 已隐含此约束 |
| 合规性 | 用户名称列表的可见范围需符合隐私策略 | 展示他人身份 |
| 可靠性 / 成本 / 时间 / 技术性 | 按项目实际填 | 缺则标 UNKNOWN，按分诊规则处理 |

## B · G2 领域模型：POS 机买单

### 领域类（书中图 6-1 口径）

`顾客`、`收银员`、`商品`、`交易`、`小票`、`支付`、`信用卡`、`会员卡`、`现金`、`购物卡`、`屏幕`、`键盘`、`扫描仪`

### 类筛选（关键一步，必须给理由）

| 领域类 | 是否转软件类 | 理由（书中口径） |
|---|---|---|
| 顾客 | **否** | 是业务领域的重要参与者，但不是 POS 机内部要实现的实体；POS 软件视角下顾客甚至不直接与 POS 交互 |
| 屏幕、键盘、扫描仪 | **否** | 一般属 POS 机硬件的一部分，不是软件系统的一部分 |
| 屏幕（例外） | **是** | 若需求要求"同时支持图形界面与字符界面输出"，屏幕相关需求就进了软件系统 |
| 收银员、商品、交易、小票、支付、信用卡、会员卡、现金、购物卡 | **是** | 筛选后剩下的领域类都需转为软件类（共 9 个） |

### 属性（书中口径举例）

`商品`：条形码、名称、价格 ｜ `交易`：商品列表、日期时间、总额、支付信息 ｜ `会员卡`：会员号、积分、有效期 ｜ `现金`：数量、币别

### 这一段的判据

- 13 个候选 → 9 个转，4 个不转，**每个不转的都有理由** ← 这就是"筛选"，不是"复制"
- 若把 13 个全搬进设计模型，G2 判不通过

## C · G3 / G4：按流程推导（示例，非书中原文）

### 第一步 照猫画虎

```
筛选    → 9 个类（见上）
名称映射 → 同名软件类，先一对一
属性映射 → 直接搬领域属性
关系映射 → 交易 1..n 商品；交易 1 支付；支付 → 现金/信用卡/购物卡
```

此时**不出现**任何接口、抽象类、工厂。

### 第二步 精雕细琢（只处理已识别的变化点）

```markdown
变化点: 支付方式会新增（新卡种、新支付渠道）
时间窗: 零售业 2 年内可能变化
结论  : 把「支付方式」封装成可替换结构
选型  : 支付抽象 + 各实现（候选 Strategy，见表 tables/variation-to-pattern.md）
不选  : 不引入 Factory——当前只有一个创建点，等出现第二个再抽
依据  : 变化点=支付方式新增 | 时间窗=2年 | 模式=Strategy | 不适用条件已排除=非固定组合、分支≥3
```

### 第三步 照本宣科（辅助类）

| 辅助类 | 用途 | 注意 |
|---|---|---|
| `ReceiptPrinter` | 小票格式化与打印 | 不含业务规则；税率、折扣属于领域类 |
| `PaymentRepository` | 支付记录持久化 | 只做存取，不做支付决策 |

### G4 双向核对表（交付物必附）

| 设计类 | 代码位置 | 一致 |
|---|---|---|
| 交易 / 商品 / 支付 / 信用卡 / 现金 / 购物卡 / 会员卡 / 小票 / 收银员 | `domain/` | ✅ |
| `ReceiptPrinter` / `PaymentRepository` | `infra/` | ✅ |
| （代码中新增）`PaymentRetryScheduler` | `infra/` | ⚠️ 已回填设计模型 |

---

## 这条链路说明了什么

1. G1 的产出不是功能清单，而是**槽位表 + 用例 + 风险**；
2. G2 的价值在**筛选**，不在搬运；
3. G3 的第二步只处理**有变化点、有时间窗**的地方，其余一律不动；
4. G4 必须双向核对，否则模型与代码两张皮。
