# 10 · 流程闸门（L1）

四道闸门，串联不可跳（宪法 #5）。每道闸门 = 输入 + 动作 + 交付物 + **通过判据（可机械检查）** + 失败模式。

```
G1 需求模型 ──→ G2 领域模型 ──→ G3 设计模型 ──→ G4 实现模型
     ↑                ↑               ↑               ↑
   缺口未闭合则阻塞（宪法 #4），不许带病进入下一阶段
```

---

## G1 · 需求模型

**输入**：客户原话 / 访谈记录 / 现有系统行为 / 竞品截图
**动作**：填 14 槽 → 写用例（主流程 + 异常流）→ 出功能列表
**交付物**：`需求槽位表.md`、`用例-UCxx.md`、`功能列表.md`

### 通过判据（全部满足）

1. 14 槽无空槽，每槽为 `KNOWN` / `ASSUMED` / `UNKNOWN` 之一
2. 无 `UNKNOWN` 且级别为 B 的槽
3. 每条功能能追到某个用例编号；每个用例能追到某个 5W1H 槽
4. 每个用例含：正常处理、**至少 2 条异常处理**、用例价值、约束和限制
5. 每条"需求"通过价值测试（对客户有价值），通过不了的是功能，要降级

### 失败模式（出现任一即判不通过）

- 把功能当需求："系统要提供扫描、收银、打印"
- 8C 全空或只填性能
- 用例只写正常流（书里明确要求"第二步：异常处理"）
- 直接开设计：跳过 G1 给出类图
- 客户说"我要个 POS 机"，照着字面做了 POS 机的界面和收银流程，没问"买单"这一层价值

### 14 槽位表（5W1H8C）

| # | 槽 | 探针问句 | 缺失后果 | 默认级别 |
|---|---|---|---|---|
| 1 | When | 什么时间/季节/班次发生？凌晨还是白天？ | 影响交互设计与容错要求 | A（涉及时段作业则 B） |
| 2 | Where | 室内/室外？哪个国家地区？ | 影响合规、设备、网络假设 | A |
| 3 | Who | 哪些参与者？含非人类参与者（系统、设备） | 影响权限与角色模型 | **B** |
| 4 | What | 做什么、产出什么、谁能看见结果 | 无此项无法建模 | **B** |
| 5 | Why | 为什么做？不做会怎样？ | 无法做价值判断与优先级 | **B** |
| 6 | How | 流程怎么走？正常流 + 异常流 | 用例缺失，领域模型无来源 | **B** |
| 7 | 性能 | 响应时间、吞吐量、并发量级 | 架构选型错误，返工成本最高 | **B** |
| 8 | 成本 | 预算上限 | 方案超出可接受范围 | A |
| 9 | 时间 | 交付节点 | 影响范围裁剪 | A |
| 10 | 可靠性 | 允许停机时长、数据丢失容忍度 | 影响存储与容灾方案 | **B**（资金/医疗类强制 B） |
| 11 | 安全性 | 是否涉及钱、身份、社保号、医疗数据 | 事后补安全 = 重构 | **B** |
| 12 | 合规性 | 行业标准/法规（3C、SOX、3GPP、ITUT 等） | 上线被卡，可能整体重做 | **B** |
| 13 | 技术性 | 客户是否锁定技术栈/平台 | 技术选型返工 | **B**（客户已锁定则强制） |
| 14 | 兼容性 | 要与哪些既有系统/协议/数据格式对接 | 集成阶段爆炸 | **B** |

> 出处：4.3.2（5W1H8C，"需求分析 518 方法"）。B/A 分级为本包新增（宪法 #4）。

### 分诊规则：问，还是自己定？

```
决定错了 → 是否触及「领域模型」或「对外契约」？
  是 → B 级，必须问（阻塞 G1）
  否 → 是否可逆且局部（改动 ≤ 半天）？
        是 → A 级，自己定，标 ASSUMED
        否 → 降为 B 级，问
```

### 提问模板（宪法 #12）

```markdown
【G1 需求闸门 · 3 项阻塞缺口】（按阻塞度降序，≤5 题）

Q1 <问题，必须是选择题或确认题>
   推荐：<我的答案>
   理由：<一行，引用已知信息>
   选错的后果：<返工范围与量级>
   若无回复：按推荐继续，登记为 ASSUMED-B1

Q2 ...
Q3 ...

以上 3 项不回复我将按推荐答案继续，并在交付物首页列出《假设与待确认清单》。
```

禁止：开放式提问（"你想怎么做？"）、一次超过 5 题、只列问题不给推荐。

### 反死锁（人类不回复）

1. 按推荐答案继续，登记 `[ASSUMED-B1]`
2. 把该假设做成**可替换点**（接口 / 配置 / 策略类），不散落在业务代码（宪法 #10）
3. 交付物首页固定输出：

```markdown
## 假设与待确认清单
| 编号 | 假设内容 | 依据 | 影响面 | 回滚方式 |
|---|---|---|---|---|
| ASSUMED-B1 | 订单不含支付 | 状态机无支付态 | 订单聚合 | 抽出 Payment 聚合 |
```

## G2 · 领域模型

**输入**：G1 的用例文档（唯一合法输入）
**动作**：找名词 → 加属性 → 连关系
**交付物**：`领域模型.md`（类 + 属性 + 关系与重数）

### 通过判据

1. 每个领域类能指到某条用例原文中的名词（注明 UC 号 + 原句）
2. 每个属性挂在正确的类上（属性不是类）
3. 关系有重数（1..n / 0..1），且不是 ER 图的关系类型
4. 无「数据库表名」形态的类（如 `t_order_item`）
5. 参与角色（人）与系统内实体已区分开

### 失败模式

- 把数据库表结构直接翻译成领域类
- 把属性立成类（`价格`、`数量` 单独成类）
- 关系只画连线不给重数
- 把"顾客"这种**业务参与者**当成软件实体（见下）

> 关键判断（书里 POS 机实例）：`顾客` 虽是领域参与者，但不是 POS 软件系统内部要实现的实体 → 不转为软件类。`屏幕/键盘/扫描仪` 一般属硬件，**除非**有"同时支持图形界面与字符界面"这类需求，才转为软件类。
> 出处：6.2.1（类筛选）

## G3 · 设计模型

**输入**：G2 的领域模型
**动作**：三步走，顺序不可换

```
第一步 照猫画虎：领域类 → 软件类（筛选 → 名称映射 → 属性映射 → 关系映射）
第二步 精雕细琢：套设计原则（C07）与设计模式（C08），只处理已识别的变化点
第三步 照本宣科：拆分辅助类（工具类、工厂、DAO、DTO 等）
```

**交付物**：`设计模型.md`（类模型 + 动态模型 + 每个抽象的"依据"行）

### 通过判据

1. 每个软件类可追溯到某领域类，或标注为"辅助类"并说明用途
2. 每个抽象（接口/抽象类/模式）附：变化点 + 变化时间窗 + 依据（宪法 #7、#8）
3. 无"设计里有、代码里没有"的类（G4 会双向核对）
4. 动态模型按需选择，不要求四张全画（见 C09）
5. 过度设计自查：每个抽象回答"如果这个变化 1 年内不发生，这段抽象的成本是多少？"

### 失败模式

- 第二步跳到模式选型，没先说变化点
- 为 5 年后的变化做设计（NOP 违反，见 C07）
- 辅助类在第一步就出现（比如一开始就 `OrderHelper`）
- 动态模型四张全画，画完没人看

## G4 · 实现模型

**输入**：G3 的设计模型
**动作**：映射到目标语言构造 → 编码 → 回填差异
**交付物**：代码 + `实现映射.md`

### 通过判据

1. 类集合双向一致：设计里的类都在代码里；代码里的类都在设计里（或已回填设计）
2. 访问控制、继承、多态、抽象类、接口的用法与设计意图一致（语言差异只影响写法，不影响结构）
3. 每个 `TODO(BLOCKING)` 已闭合或有对应假设编号
4. 假设清单与代码中的可替换点一一对应

### 失败模式

- **设计蒸发**：写完代码，设计文档没回填，模型与代码两张皮
- 语言特性替代设计：用 `private` 掩盖本该抽出去的依赖
- 把 `TODO` 带进交付

---

## 回退规则（发现型缺口）

进入 G2 之后若发现 G1 的缺口：

| 缺口性质 | 处置 |
|---|---|
| 不影响领域边界（命名、文案、日志） | 直接定，登记 ASSUMED |
| 影响领域边界或对外契约 | **回退到 G1**，一次性问完（≤5 题），不许在设计阶段边做边问 |
| 影响 8C（性能/合规/安全） | 立即停，回退 G1，标记为阻塞 |

同一轮任务内，回退 G1 只允许一次。第二次回退说明 G1 判据被绕过，重做 G1。
